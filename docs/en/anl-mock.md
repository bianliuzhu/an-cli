# mock Command

`anl mock` generates Mock.js JSON templates for `mock-service-plugin` from API files and TypeScript response declarations previously generated by `anl type`. It does not fetch Swagger, execute application API modules, or start a mock server.

If the CLI is not installed, follow the [anl installation guide](en/install). No AI tool or `anl skill` setup is required; the latter initializes instructions for AI tools, as described in the [skill command](en/anl-skill).

## Install the Mock Server Plugin

Package download and usage documentation: [mock-service-plugin on npm](https://www.npmjs.com/package/mock-service-plugin).

If the consuming project does not have the plugin installed, run **one** of these commands in that project's root directory, using its existing package manager:

- npm: `npm install -D mock-service-plugin`
- pnpm: `pnpm add -D mock-service-plugin`
- Yarn: `yarn add -D mock-service-plugin`

The package manager downloads and installs the plugin and its dependencies; no manual source download is required. The plugin already includes `mockjs` as a runtime dependency. Install `mockjs` separately only if your own application code imports it directly.

Generating mock files does not require the plugin; serving them over HTTP does. `anl mock` neither installs nor starts the plugin automatically. Follow the plugin documentation to integrate `startServer({ mockDir, port })`, pointing `mockDir` at the generated output directory. If the project already has an `npm run mock` script that starts the server, keep using it.

## Usage

Run `anl type` in the project root first, then:

```bash
anl mock
anl mock -S growth
anl mock -S growth,user
anl mock --all
anl mock -S growth --overwrite
anl mock -S growth --mock-dir mocks --log-level verbose
```

Configuration is loaded from `an.config.ts`, falling back to `an.config.json` only when the TypeScript file is absent. Generated service files are discovered in `saveApiListFolderPath`; declarations, barrels and helper modules are excluded. The checkbox lists services, not individual endpoints. Names use `swaggerConfig.name` when available, otherwise the API filename without its extension.

Select multiple services or leave the selection empty for all. A single service is selected automatically. Non-interactive terminals also process all services unless `--service` is provided.

| Option                    | Description                                                                           |
| ------------------------- | ------------------------------------------------------------------------------------- |
| `-S, --service <names>`   | Comma-separated, case-insensitive service names or API filenames without extensions   |
| `-a, --all`               | Process all generated services without prompting; mutually exclusive with `--service` |
| `-d, --mock-dir <path>`   | Override the output root directory                                                    |
| `--overwrite`             | Explicitly overwrite existing mocks; the default is to skip them                      |
| `-l, --log-level <level>` | `silent`, `error`, `warn`, `info`, or `verbose`                                       |

## Files and Server

The default output is `mocks/<service-file-stem>/<exported-function-name>.json`. Service directory names use the same sanitization as `anl type`.

For example, `appGrowthSurvey_code_GET` produces `mocks/growth/appGrowthSurvey_code_GET.json`. A URL containing `${code}` becomes `/app/growth/survey/:code`. A shortened example:

<!-- prettier-ignore -->
```jsonc
/**
 * Survey response
 * @url /app/growth/survey/:code
 * @method GET
 */
{
	"code": 10000,
	"msg": "success",
	"data": {
		"id": "@guid",
		"version": "@integer(0,100)"
	},
	"success": true
}
```

These files contain a leading comment followed by JSON. They are not plain JSON documents: the plugin strips the header, parses the body with `JSON.parse`, then renders it with `Mock.mock()`. The body must be strict JSON without trailing commas or additional comments. `mock-service-plugin` scans recursively, so keep `startServer.mockDir` pointed at the root `mocks` directory.

## Start the Mock Server

For a first-time integration, use this standalone setup. Node.js 22 or 24 is recommended. Create `scripts/mock-server.mjs` in the consuming project. The `.mjs` extension supports ESM directly without changing the project's `type` setting or installing a TypeScript runner:

```mjs
import { mkdirSync } from 'node:fs';
import { fileURLToPath } from 'node:url';
import { startServer } from 'mock-service-plugin';

const mockDir = fileURLToPath(new URL('../mocks/', import.meta.url));
mkdirSync(mockDir, { recursive: true });

startServer({ mockDir, port: 3008 });
```

`mockDir` must match `mock.mockDir` in `an.config.ts` or the directory specified through `--mock-dir`. If `3008` is occupied, choose a free port and update the frontend development proxy accordingly.

Merge these commands into the existing `scripts` section of the project's `package.json`, preserving other scripts:

```json
{
	"scripts": {
		"mock:generate": "anl mock",
		"mock:server": "node scripts/mock-server.mjs"
	}
}
```

After generating the API files, generate mocks and start the server:

```bash
npm run mock:generate -- -S growth
npm run mock:server
```

Replace `growth` with an actual service name. With pnpm/Yarn, use `pnpm run mock:generate -S growth` or `yarn mock:generate -S growth`, then `pnpm run mock:server` or `yarn mock:server`.

From another terminal, check a real endpoint, for example:

```bash
curl 'http://localhost:3008/app/growth/survey/example-code'
```

Start the frontend development server separately and proxy the requests you want to mock to `http://localhost:3008`. Preserve the complete path from `@url`, such as `/app/...` or `/dot-ai-agent/...`. Neither file generation nor server startup automatically changes application request URLs. Use the plugin for development only, not in production startup.

If an existing `npm run mock` already calls `startServer({ mockDir, port })`, as in app-h5-view's Nuxt mock mode, keep using it. Do not start a second mock server alongside it.

## Configuration

Add optional `mock` settings to your existing configuration, retaining `swaggerConfig` and other project settings:

```ts
import { defineConfig } from 'anl/config';

export default defineConfig({
	saveApiListFolderPath: 'app/apis',
	saveTypeFolderPath: 'app/types',
	mock: {
		mockDir: 'mocks',
		arrayLength: 1,
		maxDepth: 8,
		responseDefaults: { code: 10000, msg: 'success' },
	},
});
```

Each `swaggerConfig` service can override `mock.arrayLength`, `mock.maxDepth`, and `mock.responseDefaults`. Response defaults merge by field and only replace declared root fields, never add fields. Relative paths resolve from the project root. `arrayLength` accepts 1-100; `maxDepth` accepts 1-30. Configure the plugin to scan the same `mockDir`.

## Type Resolution

- The TypeScript Compiler API resolves generated request calls and referenced declarations. Analysis uses the `serve` overload in memory to infer the HTTP envelope through types such as `RServe<T>` and `ResponseModel<T>`. API files remain unchanged; `data` and `axios` return levels do not change the generated HTTP payload.
- Custom request methods that return the response directly do not gain an envelope. Responses already containing equivalent envelope fields are not wrapped twice. Missing declarations produce an error instead of executing application modules.
- Recognized envelopes use success defaults for broad scalar types: `success: true`, `code: 10000`, `msg/message: 'success'`, and generation-time `timestamp` when that numeric field is declared. Literal constraints take precedence. Configure `responseDefaults` for other success codes. Undeclared fields are never added.
- References, interfaces, aliases, objects, arrays, tuples, intersections, mapped types and typed dictionaries are expanded recursively. Optional properties are included where possible; `never` properties are omitted.
- Scalars use `@string`, `@integer(0,100)` and `@boolean`. Names, `@format`, and `@example` help recognize UUIDs, dates, email addresses and URLs; example values are not copied verbatim.
- UUIDs and common string ID fields use `@guid`. Mock.js `@id` generates a Chinese identity-card number, not a generic identifier.
- Literal values remain unchanged. Literal unions and enums use `@pick([...])`. Other unions choose the first non-null branch rather than merging unrelated alternatives.
- Arrays contain one expanded element by default, configurable through `arrayLength` and capped by declared `@maxItems`. Dictionaries use sample keys, without guessing relationships to other fields.

## Protection and Limits

Existing mocks are identified recursively by method and normalized URL, including equivalent parameter names such as `:id` and `:code`. Target files and flat legacy files with the same name are also protected. By default they are skipped.

`--overwrite` updates existing files in place, including the legacy flat layout. It never clears the directory, deletes stale endpoints, or overwrites a conflicting mock in another service directory. Ambiguous files and duplicate selected routes fail before writes begin. The plugin cannot distinguish identical routes by upstream service; folders are not route namespaces. Symbolic links inside `mockDir` are rejected.

Unknown values fall back to `null`; `Record<string, unknown>` falls back to `{}` with a warning. Types alone cannot reveal missing keys such as `en/zh` or `id/status`. Cycles, maximum depth and a 10000-node expansion budget truncate output and may require manual completion. String patterns that cannot be inferred safely also produce placeholders and warnings.

Only JSON templates are generated, not streams, file responses or complete business scenarios. Cross-array IDs, tag/color relationships and success-code semantics require explicit types or manual adjustments.

## Inspect Generation Warnings

```bash
anl mock -S agent --log-level verbose
```

`field(s) need review` counts field locations, not failed endpoints. Detailed output identifies the endpoint, field path and reason. For example, `dictionary values have no inferable structure; emitted {}` means a dictionary has no concrete field structure, while `unknown ... emitted null` means the value type is unknown. These warnings do not prevent other fields or endpoints from being generated.

Increasing `maxDepth` only helps with `maximum depth ... reached`; it cannot supply missing `unknown` structure or eliminate cycles. Define concrete types for fixed structures, then regenerate, or manually complete mocks for dynamic JSON.

`generated` counts new files, `overwritten` counts explicit replacements, and `skipped` counts preserved existing files. Diagnostics are collected before deciding which files to skip, so skipped endpoints can still produce warnings. Do not add `--overwrite` just to inspect warnings; use it only when you intend to update existing files.

Start the plugin with the `npm run mock:server` script above or your project's existing `npm run mock` command after generation.
